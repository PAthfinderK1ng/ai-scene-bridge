## 0.5 调研结论对本设计的影响（报告出来后补）

**四个痛点的判定**：P1 部分成立（空间理解弱是真的，"靠代码"不是缺陷，问题在喂给代码的空间表示）；P2 成立（反方也反驳不了，是本方案唯一站得住的核心）；P3 部分成立（作为沟通问题已有定式：hex 色板 + 参考图 + 数值材质参数，中间层增量真实但小）；P4 部分成立（"不会搭"不成立，灰盒本就是第一步；"没资产 / 不会用资产 / 不能按体块硬约束尺寸"成立，且不是中间层能解的）。

**对方案的判定**：技术可行，但**"独立 Web 工具里摆方块再导 JSON"这一形态没有必要性**。摆体块这件事引擎 + MCP 已免费覆盖（unity-mcp 含 ProBuilder 工具、UE 5.8 官方约 824 个 MCP 工具、blender-mcp）。中间层能提供而引擎内 blockout 没有的只有三样：

1. **事前意图层**：语义标注（这是门 / 掩体 / 地标 / 视线要通到哪）、参考图与 hex 色板绑定到具体体块、可玩验收条件；
2. **预计算关系**：邻接、朝向、遮挡、可达、贴墙、叠放，提前算好写进 JSON，不让 AI 从原始几何推（FloorplanQA：LLM 读 JSON 布局时距离/可见性可靠，放置可行性/最短路径大幅下滑）；
3. **校验器**：门洞被挡、穿模、悬空、越界、无光、尺度越界，输出 Agent 可读的报告，作为验收步骤。失败集中在"写"端（Magnopus：有精确坐标仍墙绕中心、椅背对桌），只改善输入不够。

**形态**：优先 **Unity 插件 + Claude Code Skill**（Unity 官方 unity-agent-plugin / skills 的 34 个技能里没有场景布局技能，是个可以直接填的洞），不做独立编辑器；UE 第二阶段；限室内 / 模块化关卡；不碰资产生成、地形、PCG。

**导出格式的两个硬结论**：(a) **语义层必须是 sidecar JSON**，不能只靠 glTF extras：UE Interchange 不暴露 node.extras，Unity glTFast 6.x 默认丢 extras（本设计的 scene.sid.json 已经是主文件，方向对）；(b) **结构化文本为主、图为辅**：LayoutVLM 消融显示去掉图像后位置/旋转几乎不变、图像主要改善碰撞；WorldAuditBench 中前沿模型看截图找异常只有 6.6–42.3%；Epic 的标注截图单次 >1M token。所以实验里 "JSON" 与 "JSON + 图" 必须分开测。

**对已经做出来的网页编辑器（app/）怎么办**：它不该是产品首发形态，但不用扔。它的定位改为两件事：(1) **实验输入端**，用来生成对照实验里 B（文字 + 标注俯视图）、C（JSON + 预计算关系）两组的输入包，以及 D 组的灰盒 glb；(2) **SID 格式与校验器的试验台**，关系预计算、校验规则、导出包结构先在这里迭代，成熟后搬进 Unity 插件。接下来不再给编辑器加"像引擎"的功能，而是把精力放在：关系预计算（现在 relations 全靠手填）、校验器补齐报告 §5.1 第 4 条的规则、Unity 导入 / 读回脚本与 Skill。

**实验设计改为四组**（详见 [experiments/week0-ab](../experiments/week0-ab/README.md)）：A 纯文字；B 文字 + 标注俯视图；C JSON + 预计算关系（无图）；D 引擎内灰盒（导入 scene.glb）由 Agent 经 MCP 读层级后只做"上装"。判读规则：C ≫ A/B 且 C ≈ D → 价值在"预计算关系 + 语义 / 色彩标注"，做插件；D ≫ C → 放弃独立输入端，只做标注 + 校验插件；A ≈ C → 重新审视 P2。

**必须承认的风险**：没有任何对照数据证明中间层优于"引擎里搭灰盒 + MCP 读层级"；引擎厂商正在免费覆盖周边（Unity Generators 图→布局、团结 2.0 "AI 友好数据格式"、UE6 内建 LLM），schema 本身无护城河；可触达的付费用户极少。报告的原话：这更像"能被 Unity / Epic 吸收或变成社区标准的工具"，而不是能独立长成公司的产品。

## 0. 一句话

中间层 = **一份场景意图文件（Scene Intent Document，下称 SID）** + 围绕它的四个小件：查看编辑器、校验器、引擎编译器（含读回）、AI 协议。
**文件是产品，编辑器只是它的一个前端。** 任何能产出或消费 SID 的东西（Web 工具、ProBuilder 导出脚本、UE Python、Claude Code）都是这个媒介的一部分。

```
                 文字 / 参考图
                      │
                      ▼
   ┌────────── AI: Draft ──────────┐          ┌──────────────── 引擎 ────────────────┐
   │ 读文字 → 写 SID 草稿（几秒）    │          │ Unity  (C# Editor 脚本 / MCP)         │
   └───────────────┬───────────────┘          │ UE     (Python Editor Scripting / MCP)│
                   ▼                          └───────▲───────────────────┬──────────┘
          ┌─────────────────┐   导出包（sid.json      │ Compile            │ Read-back
          │  查看编辑器      │   + 俯视图 + 透视图     │                    ▼
   用户 ─▶│  看 / 拖 / 标注  │───+ 调色板 + 参考图）──▶ AI: Compile      SID'（引擎里实际的样子）
          │  取色 / 校验     │                                            │
          └─────────────────┘◀──────────── diff(SID, SID') ──────────────┘  AI: Verify
```

## 1. 两条流程

### A. 生成后引导（主流程，对应"AI 凭空生成"）

| 步 | 谁 | 做什么 | 产物 |
| --- | --- | --- | --- |
| 1 | 用户 | 一段文字 + 可选参考图 | prompt |
| 2 | AI (Draft) | 不写引擎代码，先写 SID：体块、语义、相对关系、调色板 | `scene.sid.json` v1 |
| 3 | 编辑器 | 渲染 SID，用户看三秒、拖两下、改标签、换颜色 | v2 |
| 4 | 校验器 | 重叠、越界、尺度、可达性 | 警告列表 |
| 5 | 编辑器 | 导出包：SID + 俯视图 + 透视图 + 调色板 + 参考图 | `export/` |
| 6 | AI (Compile) | 在 Unity / UE 里按 SID 建体块、换资产、刷材质、建地形、打灯 | 引擎场景 |
| 7 | 引擎脚本 | 读回场景为 SID' | `readback.sid.json` |
| 8 | AI (Verify) | diff(SID v2, SID')，列出位置 / 尺寸 / 朝向 / 缺漏偏差，修正 | 修正后的场景 |

关键点：**AI 先写中间表示，然后人和 AI 都读它。** 读引擎场景只发生在第 7 步，目的是验证，不是采集意图。

### B. 用户先摆（辅流程）

跳过第 2 步，用户在编辑器里从零摆体块，其余相同。给已经有明确画面的人用。

## 2. SID 文件格式 v0.1

### 2.1 设计原则

1. **声明式**：描述"场景是什么"，不描述"怎么建"。不含任何引擎 API。
2. **引擎无关**：一份文件进 UE 也进 Unity，差异全部放在编译器里。
3. **人可读、AI 可写**：JSON，键名是英文单词，ID 是人能看懂的 `house_1`，数字默认吸附到 0.5 m 网格，避免 `3.1415927` 这种 AI 不擅长的数字。
4. **相对关系显式**：除了绝对坐标，还有 `relations`（朝向、相邻、可见），这是 LLM 最擅长的表达方式；几何能推导的关系由编辑器导出时自动补全，不靠 AI 算。
5. **图文并用**：导出包必带俯视图和透视图。模型读图抓整体感，读坐标抓精度，缺一不可。
6. **小而稚**：v0.1 只有体块、区域、路径、标记、地形特征五类对象，不做网格编辑。

### 2.2 坐标约定

| 项 | SID | Unity | UE |
| --- | --- | --- | --- |
| 单位 | 米 | 米 | 厘米 |
| 上轴 | +Y | +Y | +Z |
| 手性 | 右手（同 glTF） | 左手 | 左手 |
| 北 / 前 | −Z | +Z | +X |
| 位置换算 | (x, y, z) | (x, y, −z) | (−z·100, x·100, y·100) |
| 绕上轴旋转 | `rotation_y` 度，0 = 面朝北 | −rotation_y | yaw = −rotation_y |

换算公式必须用往返测试（SID → 引擎 → 读回 → 与原 SID 比对）验证，不要相信推导。`meta` 里显式写出 `units / up_axis / handedness / north`，让读文件的人和模型都不用猜。

### 2.3 顶层结构

```
sid_version   格式版本 "0.1"
meta          名称、作者、时间、单位与坐标约定、玩家身高、网格
intent        一段话总结、情绪词、玩法类型
style         调色板（HEX + 角色 + 备注）、参考图、光照 / 时段、材质意图
bounds        场景包围盒 min / max
terrain       基底类型 + 地形特征（山丘、坑、台地、悬崖）
volumes       体块：建筑、墙、平台、岩石、道具占位、水体、掩体
regions       区域：多边形 + 用途（广场、林地、农田、危险区、遭遇区）
paths         路径：折线 + 宽度 + 用途（道路、小径、河流、围墙线）
markers       点：出生点、目标、敌人刷新、灯、相机、兴趣点
relations     对象间关系：faces / adjacent / on_top_of / inside / visible_from / connects / blocks
constraints   约束：locked / min_clearance / keep_inside / max_count / must_reach
views         导出的图：俯视正交图（含比例尺）、透视图（含相机参数）
asset_hints   每个对象的资产检索词 / 生成提示词 / 适配方式 / 兜底
```

完整字段见 [spec/sid.schema.json](../spec/sid.schema.json)，手写示例见 [spec/examples/village-square.sid.json](../spec/examples/village-square.sid.json)。

### 2.4 一个体块长什么样

```json
{
  "id": "house_1",
  "kind": "building",
  "shape": "box",
  "position": [-10, 0, -6],
  "size": [6, 4, 5],
  "rotation_y": 20,
  "label": "木屋",
  "material_intent": "木板墙 + 茅草顶，门朝广场",
  "color_role": "wall",
  "importance": "primary",
  "notes": "村里最大的一栋，门口有台阶"
}
```

`position` 是底面中心（不是几何中心），这样"放在地上"就是 y = 0，AI 不用算一半高度。

### 2.5 为什么这样选

- **JSON 而不是 YAML / 自造 DSL**：所有语言零成本解析，JSON Schema 可直接校验，LLM 对 JSON 的输出稳定性最好。
- **伴随一份 glTF**：导出包里同时给 `scene.glb`，体块作为 mesh，`extras` 里带 `id / kind / label`。两个引擎都原生导入 glTF，编译器拿到几何不用自己建。但语义层仍以 `sid.json` 为准。
- **不用 USD**：对一个人的项目太重；UE 支持好但 Unity 弱；LLM 对 USDA 的熟悉度也不如 JSON。等需要和 DCC 流水线接轨再说。
- **位置 + 相对关系都存**：绝对坐标给编译器，相对关系给模型；两者冲突时以坐标为准，编辑器导出时重新推导关系。

## 3. 给 AI 看什么：导出包与协议

```
export/
├── scene.sid.json      语义与几何（主文件）
├── scene.glb           体块几何（可选，给引擎直接导入）
├── views/
│   ├── top.png         俯视正交图：北朝上、网格、坐标刻度、比例尺、每个对象的 id + label + 尺寸 + 朝向箭头
│   └── iso.png         鸟瞰透视（编辑器）或正交等轴测（Python 脚本）
├── assets/             编辑器导入的素材原文件（可选）
├── refs/               用户贴的参考图（可选）
├── README.txt          文件说明
└── PROTOCOL.md         告诉 AI 怎么读这个包、怎么编译、怎么验证
```
（文件清单以 [spec/PROTOCOL.md §0](../spec/PROTOCOL.md) 为准。）

AI 侧三个"技能"（Claude Code 的 skill / Cursor 的 rules，内容就是 PROTOCOL.md）：

| 技能 | 输入 | 输出 | 规则要点 |
| --- | --- | --- | --- |
| Draft | 文字 + 参考图 | SID | 单位米、玩家 1.8 m、吸附 0.5 m 网格、先定地标再摆其它、不重叠、每个对象写 label 和 notes、补 relations |
| Compile | 导出包 | 引擎场景 | 先全部用体块复现（保证布局），再逐个按 asset_hints 换资产并缩放到体块尺寸，再按 style 刷材质、建地形、打灯；每步截图 |
| Verify | SID + 读回 SID' | 偏差清单 + 修正 | 位置差 > 1 m、尺寸比 > 1.3、朝向差 > 20°、缺漏对象都要报；先修布局再修外观 |

## 4. 编译到引擎

### Unity

- v0：C# Editor 脚本 `SidImporter.cs`，菜单一键读 JSON，按 `volumes` 建 GameObject（Cube / Cylinder 或 ProBuilder），按 `regions` 铺平面或 Terrain Layer，按 `paths` 用 LineRenderer / Spline 占位，按 `markers` 放空物体，材质按 `color_role` 从调色板取色。
- v1：把同样的逻辑包成 MCP 工具（现有的 Unity MCP server 都能执行 C# / 建对象），让 Claude Code 直接调。
- 读回：`SidExporter.cs` 遍历带 `SidId` 组件的对象，反算到 SID 坐标系，输出 `readback.sid.json`。

### UE

- v0：Python Editor Scripting `sid_import.py`：`EditorLevelLibrary.spawn_actor_from_class` 放 StaticMeshActor（BasicShapes），按 size 设 scale，`Landscape` 先不碰，地形特征用大体块或 ProceduralMesh 占位。
- v1：接 Unreal MCP 或 Remote Control API；地形用 PCG 或 Landscape Python 接口。
- 读回：遍历带 tag `sid:<id>` 的 Actor。

### kind → 资产映射（v0 用体块，v1 用表）

| kind | v0 体块 | v1 资产来源 |
| --- | --- | --- |
| building | 盒子 | 资产库检索（`asset_hints.search`）→ 缩放到体块；或 Meshy / Tripo / Hunyuan3D 按 `generator_prompt` 生成 |
| rock / prop | 盒子 / 圆柱 | 同上 |
| forest 区域 | 绿色平面 | 在多边形内按密度散布树木预制体 |
| road 路径 | 窄平面 | Spline mesh 或贴花 |
| hill 地形特征 | 半球 / 锥 | Terrain 高度图叠加高斯 |

## 5. 查看编辑器 MVP

### 形态选择

| 形态 | 优点 | 缺点 | 判断 |
| --- | --- | --- | --- |
| **Web 独立工具（Three.js）** | 秒开、跨平台、非程序员可用、引擎无关、好分享、迭代快 | 要自己做 gizmo / 相机 / 吸附 / 撤销（drei 基本都有现成件） | **v0 选它** |
| Unity 内插件 | 直接用引擎编辑器，不重造轮子 | 绑死 Unity；非程序员要装 Unity；要做两套 | 作为"导出端"做，不作为主体 |
| UE 内插件 | 同上 | 同上，且 UE 更重 | 同上 |
| Blender 插件 | 建模能力强 | 目标用户未必会 Blender；离引擎远 | 不做 |
| 仅规范 + 脚本 | 最轻 | 没有"看三秒拖两下"的体验，P2 解不干净 | 作为第 0 周实验的形态 |

### 功能清单

必须（第 1–2 周）：
- 打开 / 保存 SID；网格地面；俯视正交与透视两个相机，一键切换
- 选中、移动、缩放、绕 Y 旋转（TransformControls），吸附 0.5 m
- 添加 / 删除 盒子、圆柱；画多边形区域；画折线路径；放标记
- 右侧属性面板：id、kind、label、material_intent、color_role、notes
- 调色板面板：角色 + HEX + 备注；取色器；参考图拖入
- 校验器结果列表，点击定位
- 导出包：sid.json + top.png（带标注与比例尺）+ cam.png + glb

可选（第 3–4 周）：
- 「从文字生成草稿」按钮（调 Claude API 跑 Draft 技能）
- 读回 SID' 的叠加显示与 diff 高亮
- 地形特征的可视化（高斯山丘）

明确不做：网格编辑、材质编辑器、灯光烘焙、任何"像引擎"的功能。

### 技术选型

Vite + React + TypeScript；three + @react-three/fiber + @react-three/drei（TransformControls、OrthographicCamera、Grid、Html 标签）；zustand 存状态与撤销栈；ajv 用 `sid.schema.json` 校验；three 的 GLTFExporter 导 glb；JSZip 打包导出。单人、无后端、纯静态部署。

## 6. 校验器规则（v0）

1. 所有对象在 `bounds` 内
2. `volumes` 之间不重叠（旋转盒按 OBB 近似），`markers` 不在体块内部
3. `paths` 两侧满足 `min_clearance`
4. `relations / constraints` 引用的 id 都存在
5. 尺度合理：building 高 ≥ 2.5 m；prop ≤ 3 m；玩家 1.8 m 能过的门洞 ≥ 2.2 m（有 `door` 标注时）
6. 可达性：以 0.5 m 栅格把地面减去体块，从 `player_spawn` 泛洪，`must_reach` 的目标必须可达
7. 关系一致性：`faces` 的 a 的朝向向量必须大致指向 b（夹角 < 45°）；`adjacent` 的间距 < 2 m；`inside` 的中心在多边形内；`far_from` 的间距 > 对象尺寸。第一版手写示例里四栋房子的 `rotation_y` 就全部背对了井，渲染成俯视图一眼看出，纯读 JSON 看不出来，这正是「图 + 关系校验」要兜的底

## 7. 分期计划

| 期 | 内容 | 完成标志 |
| --- | --- | --- |
| 第 0 周 | 不写编辑器。手写 1 份 SID（已给示例）+ 手画 1 张俯视图。同一场景做 A/B：A 纯文字，B SID + 俯视图，都交给 Claude Code + Unity MCP 复现 | 一张对比表：位置 / 尺寸 / 朝向 / 缺漏 / 颜色，B 明显优于 A 则继续 |
| 第 1–2 周 | Web 编辑器「必须」功能 + 导出包 | 10 分钟内从零摆出示例村庄并导出 |
| 第 3 周 | Unity `SidImporter / SidExporter` + PROTOCOL.md；跑通 A 流程 1–8 步 | 往返测试：导出 → 导入 → 读回，位置误差 < 0.5 m |
| 第 4 周 | UE Python 导入 / 读回；校验器；diff 可视化 | 同一份 SID 在两个引擎里布局一致 |
| 之后 | **外观层**（见 9.5）：素材导入并画进俯视图 / 参考图槽位 / 按体块生成资产 / 地形高度图；「从文字生成草稿」 | 看第 0 周与报告结论再定 |

## 8. 成功指标（A/B 实验与往返测试共用）

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 位置误差 | 每个对象意图中心与实际中心的距离，取均值 | < 1 m（往返 < 0.5 m） |
| 尺寸误差 | 实际 / 意图 的最大维度比 | 0.8–1.25 |
| 朝向误差 | 绕上轴角度差 | < 20° |
| 缺漏 / 多余 | 对象计数差 | 0 |
| 颜色符合度 | 人评 1–5 | ≥ 4 |
| 用户修改次数 | 达到"可接受"前的拖拽 / 改字次数 | 越少越好，作为 Draft 技能的改进信号 |

## 9. 关键决策与待定项

已定（可推翻）：
- 文件是产品，编辑器是前端；主流程是「生成后引导」而不是「用户先摆」
- JSON + 伴随 glTF；坐标用 glTF 约定；位置是底面中心；0.5 m 网格
- v0 只做体块级，不碰网格与真实资产

待定（等调研报告与第 0 周实验）：
1. 模型读「坐标 + 关系」和读「俯视图」哪个贡献更大？决定导出包里图的优先级与数量
2. 现有 Unity / Unreal MCP 能否稳定地「建体块 + 截图 + 读层级」？决定 v1 走 MCP 还是自写脚本
3. 资产替换走资产库检索还是生成 API？价格、延迟、能否按尺寸生成
4. `relations` 由 AI 写还是由编辑器自动推导？推导规则怎么定（相邻 = 间距 < 2 m？）
5. 俯视图分辨率、标注密度，模型读起来的上限在哪
6. 是否需要「分层」（地形层 / 建筑层 / 道具层）来控制 AI 的编译顺序
7. 版本化：SID 要不要记录每次用户修改（作为 Draft 技能的训练 / 评估数据）

## 9.5 外观层：目前没有解决（2026-10-17 讨论记录）

目前的 SID + 俯视图只传达**布局**：东西在哪、多大、朝哪、挨着谁。它不传达**外观**：山是陡是缓、山脊怎么走、房子是尖顶还是平顶、墙上有没有木梁。俯视图里山是三个同心圆，房子是一个矩形，AI 拿到的仍然是体块。这正是 P4，也是用户指出的"交流的困难所在"。第 0 周实验只测布局（P2），不测外观，结论不能外推到 P4。

"长什么样"怎么传，等调研报告（学术中间表示、资产生成、世界模型、风格沟通几个维度）出来再定。先记下候选方向，不做决定：

| 方向 | 做法 | 直觉上的优缺点 |
| --- | --- | --- |
| 素材导入 | 用户把现成资产（glTF / FBX / 引擎资产包）拖进中间层，直接摆真模型而不是体块；导出时带资产 id + 变换，AI 只负责放置、替换和补齐 | 最直接，外观零歧义；要做资产浏览和导入，体块也要能"升级"成资产；**导入的资产同样画进俯视图**（用它的真实轮廓而非矩形） |
| 每个对象一张参考图 | `style.references[].applies_to` 已经预留；房子贴一张茅草屋照片，山贴一张缓坡剪影 | 便宜，人类美术就是这么沟通的；AI 能"看懂"到什么程度要测 |
| 按体块生成资产 | 用 `asset_hints.generator_prompt` 调 Meshy / Tripo / Hunyuan3D，生成后缩放进体块 | 不需要资产库；质量、风格一致性、价格、延迟未知，等调研 |
| 地形用图而不是数字 | 山丘不用 radius/height，改用高度图（灰度 PNG）或一条侧视剖面草图 | 数字说不清山的形状，图能；编辑器里画高度图比摆体块难 |
| 形状语法 / 预设 | 对 building 之类的 kind 提供几种参数化外形（坡顶 / 平顶 / 带院），用户选不是画 | 覆盖面有限，但对"小村子"这类常见题材够用 |

真正要回答的问题是：**外观信息的最小充分表达是什么**，以及它该由谁来提供（用户导入、用户贴图、AI 生成、还是预设库）。这决定编辑器下一期做"资产导入"还是做"参考图槽位"。

**调研报告给出的答案（2026-10-17 补）**：
- 走 **"先占位、后替换"**：Unity 官方把 Generators 产物定义为占位（prefab 引用不动、随时替换最终资产），Ludus AI 也是"占位体 → 批准后替换"。中间层只需在体块上留**资产绑定字段**（项目资产路径 / 检索词 / 生成提示词），不做资产生成。
- **生成 API 不能按体块硬约束尺寸**：Meshy Resize 只有等比缩放，Tripo auto_size 等比，Rodin bbox 是比例，Hunyuan3D-Omni 的 bbox 也是比例且无贴合度指标。"把 2×3×4 的盒子换成木屋"必须靠"生成 → 读包围盒 → 等比缩放贴地（必要时非等比微调或重生成）"，这正是编辑器导入素材时已经在做的事。
- **颜色数值化、风格靠参考图**：LLM 读 hex 比读色词可靠（52.6% vs 17.1%），VLM 从图里读色不可靠（ColorBench 最佳约 60%），所以调色板必须是 hex + 语义词；形体风格靠参考图绑定到体块，并要求 Agent 优先用项目材质库而不是默认材质。
- **风格一致性与风格化材质生成是生成模型的问题**，中间层解决不了，明确不做。
- 地形：报告建议首期限室内 / 模块化关卡，不碰地形与 PCG；山丘的高度图 / 剖面草图留到以后。

## 10. 与四个痛点的对应

| 痛点 | 中间层里对应的东西 |
| --- | --- |
| P1 空间理解弱 / 只会写代码 | AI 不再直接写放置代码，而是写声明式 SID；校验器与读回补上它缺的"看一眼" |
| P2 想象传不过去 | 编辑器「看三秒拖两下」+ relations + 俯视图；先猜一版再改，而不是让人先说清 |
| P3 颜色 / 风格 | style：调色板（HEX + 角色）、参考图、材质意图、光照；颜色不再靠文字 |
| P4 只会堆几何体 | 体块本来就是第一步；asset_hints + 资产库 / 生成 API 负责"长成那样" |
