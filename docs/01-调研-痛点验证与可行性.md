# AI 搭建游戏关卡场景的四个痛点验证与「中间层 3D 工具」可行性调研

> 撰写日期：2026-10-17。面向项目发起人本人。
> 证据来源：七个维度的调研 + 独立核查 + 两位反方 + 四轮补查。核查标签说明：本报告只把「已核实 / 已修正」的论断当事实用；「未核实」的内容在正文中明确标注；被推翻的论断不作为依据。调研期间 WebSearch 配额中途耗尽，大量核查依赖直接抓取一手页面，Reddit、知乎（403）、部分 CSDN（521）与 Epic 部分 JS 渲染文档未能覆盖，这是本报告的系统性盲区。

## 0. 一页结论

### 0.1 四个痛点判定

| 痛点 | 判定 | 一句理由 |
|---|---|---|
| **P1** AI 写地图全靠代码，三维理解不足 | **部分成立** | 「三维空间理解不足」成立且证据稳固：2024–2026 所有主流空间基准上前沿模型比人类低 40–55 分，相对方向、视角转换、心理旋转接近随机 [1][2][4][5]；但「全靠代码」不是缺陷而是行业公认的最优接口，blender-mcp、SceneCraft、Unity CLI 都走代码路线，问题出在喂给代码的空间表示，不在代码本身 [14][46][95]。 |
| **P2** 自然语言说不清三维，搭出来不像 | **成立** | 这是反方也承认反驳不了的一条。Unity/UE/Blender 三类环境的一手实测独立复现同类错误（墙绕中心摆、椅子背对桌、门被挡、室内无光、尺度失衡）[53][65][67]；带精确距离角度的文本仍让最强模型落后人类 15 分 [9]；LLM「读结构化空间好、写差」[23][26]，恰好论证「人画、AI 读」的分工。 |
| **P3** 不知道用户要什么色彩/材质/风格 | **部分成立** | 作为「沟通」问题已有业界定式：hex 色板 + 参考图 + 数值材质参数；LLM 读 hex 可靠（1 色补全 Hex 52.6% vs 色词 17.1%）[79]，Unity Generators / Meshy / Substance / IP-Adapter 都内置参考图槽 [45][84][90]。真正未解的是：AI 默认不会主动匹配项目既有风格（实测全用默认 Lit 材质）[53]，风格化（非写实）材质生成与多资产风格一致性没有可靠解法 [93][94]。 |
| **P4** 只会用几何体堆叠 | **部分成立** | 要区分「不会搭」与「没资产 / 不会用资产」。灰盒是关卡设计标准第一步，Unity 官方把 Generators 产物定义为「intended to be replaced before ship」[48]；Meshy/Tripo/Rodin/Hunyuan 已全面接入 MCP，单个资产约 $0.4–0.8、2–6 分钟 [90][91]。未闭合的是：资产生成不能按体块硬约束尺寸（只有比例/等比缩放）[40][90]，AI 不会主动用场景里已有资产 [69]，「体块 → 可编辑、可玩、风格一致的引擎关卡」目前没有任何产品闭合 [30][32]。 |

### 0.2 「中间层 3D 工具」可行性判定

**结论：技术可行，但「独立 Web 工具里摆方块再导 JSON」这一形态没有必要性；只有在以下三个前提下才成立。**

1. **价值必须放在「事前意图 + 预计算关系 + 校验」而不是「摆体块」**。摆体块这件事，CoplayDev/unity-mcp（含 ProBuilder 工具）、UE 5.8 官方约 824 个工具、blender-mcp（31.4k star）已经免费覆盖 [51][62][95]。中间层能提供而引擎内 blockout 没有的是：语义标注（这是门、这是掩体、视线要通到哪）、预先算好的邻接/朝向/遮挡/可达关系、参考图与 hex 色板绑定到具体体块、以及一份让 Agent 自检的校验清单（门洞被挡、穿模、悬空、无光、尺度越界）。
2. **形态优先「引擎插件 + Agent Skill」，不是独立编辑器**。Unity 官方 Claude Code 插件链路（unity-agent-plugin + Unity-Technologies/skills）已就位，而其 34 个官方技能里没有任何场景布局/关卡/地形技能，是可以直接填的洞 [49][50]。独立 Web 工具多一次学习、多一道导入导出，并面临 Marble Chisel 的心智占位。
3. **必须先用对照实验证明增量**。截至 2026-10-17，学术界与社区都没有「同一场景、纯文字 vs 结构化 JSON vs 标注俯视图 vs 引擎内灰盒读层级」的还原度对照数据 [38][35][36]。没有这个数据，无法证明中间层优于「在引擎里搭灰盒、AI 经 MCP 读层级」这条免费替代路线。

### 0.3 最重要的五条发现

1. **学术界几乎全部收敛到「中间表示」路线**：Holodeck、SceneCraft、Open-Universe、LayoutVLM、R3L、WorldGen、UnrealLLM、AutoUE 都不让 LLM 直接吐坐标，而是输出关系约束 / 场景图 / DSL / PCG 参数 / 体块 blockout 再由求解器或生成模型落地 [12][14][17][18][29][36][37]。你的设想是这条路线的「人工输入端」版本，方向有充分先例。
2. **失败类型集中在朝向、贴墙、穿插、语义命名，而不是坐标本身**。Magnopus 用 UE 5.8 官方 MCP 的实测：墙围着中心格摆、朝向错、椅子背对桌、桌子一半嵌进墙、灯具因未命名无法区分 [65]。这正是中间层要显式标注的信息，也说明光给坐标不够。
3. **「让 AI 看截图自检」成本高且不可靠**：Epic 原生 epic_capture_viewport 确有世界网格与 Actor 标注，但 base64 内联单次 >1M token [64]；WorldAuditBench 中前沿模型找漂浮/穿墙异常成功率仅 6.6–42.3%（人类 83.4%）[28]；Classmethod 实测中 AI 把自己清晰的截图判为「几乎全黑」[53]。结构化、预计算的关系比截图更可靠。
4. **「体块 → 风格化世界」已被 World Labs Marble Chisel 产品化**（墙体/挤出/GLB 模板 + 文字定风格，「decouples structure from style」）[30][31]，但它输出整体融合的高斯泼溅与重建网格而非逐物体可编辑资产，无 Chisel 编程接口，官方承认「不替代游戏管线」[34]，且 World Labs 2026-09-28 宣布加入 AMD、Marble 走向未明 [33]。真正的空位是「3D 意图输入 + 引擎资产/语义绑定 + Agent 可消费的结构化导出」这一组合。
5. **引擎厂商正在用免费功能覆盖周边**：Unity 官方 MCP server 现已免费无并发限制 [123]，Generators 有「Scene layouts from image references」[45]，Unity 中国团结引擎 2.0 明说要引入「对 AI 更友好的新数据格式」但零细节且未上线 [57][58]；Epic UE6 将内建 LLM/MCP [70]。任何「结构化场景描述」都可能在下一个引擎版本变成内置格式，所以 schema 本身不值钱，校验层与意图层才是差异点。

### 0.4 建议下一步

- **两周内**：在 Unity 6 + CoplayDev unity-mcp（或 Unity 官方 MCP/CLI）上跑一个 14 物体房间的四输入对照实验（纯文字 / 文字 + 标注俯视图 / 预计算关系的 JSON / 引擎内灰盒由 Agent 读层级），度量位置/尺寸/朝向误差、穿插越界数、轮数、token、人工修正次数（协议见 §5.2）。
- **根据结果决定**：若 JSON + 关系组显著优于纯文字且不劣于引擎内灰盒组，则做「Unity 插件 + Claude Code Skill」MVP；若引擎内灰盒组 ≈ JSON 组，则放弃独立输入端，只做「语义标注 + 校验器」插件。
- **不要先做 Web 编辑器**。

## 1. 四个痛点逐条验证

### 1.1 P1：AI 全靠代码写地图，三维空间理解不足

要把 P1 拆成两层。

**第一层：LLM/VLM 的三维空间推理能力不足——成立，证据稳固。**

- VSI-Bench（CVPR 2025 Oral，5,000+ 问答，视频输入）：人类 79.2 分，GPT-4o 34.0 分与频率基线持平，Gemini-1.5 Pro 45.4；约 71% 的错误归因于空间推理而非感知或语言；模型「形成一系列局部世界模型而非统一全局模型」[1]。
- MMSI-Bench（ICLR 2026，1,000 题）：人类 97.2%，GPT-5 41.9%，o3 41.0%，Gemini-3-pro 49.2%（排行榜），随机 25%；最大错误来源是跨视角匹配与场景重建 [2]。OmniSpatial（ICLR 2026）：o3 56.33% vs 人类 92.63%，几何推理子项仅 29.68（人类 85.90）[3]。
- 心理旋转与视角转换最弱：SpinBench（ICLR 2026）多数模型处于或低于随机 [4]；SPACE（ICLR 2025）多模态模式下视角转换 21.8/26.5（随机 25，人类 78.5/80.0）[5]。单图基础感知也仅略高于随机：BLINK 物体定位 GPT-4V 50.40 ≈ 随机 [6]；3DSRBench 朝向子项 GPT-4o 21.6（随机 16.8）[7]。
- 把场景转成带精确距离/角度的文本（SiT-Bench，2026-01 预印本）后，最强模型 59.46% 仍低于人类 74.42%；认知地图子任务最佳 8.34%（人类也只有约 26%）[9]。

**边界与反方**：差距在快速收窄而非停滞——MMSI-Bench 上 Gemini-2.5-Pro 36.9 → Gemini-3-pro 49.2；Cambrian-S-7B 专项训练在 VSI-Bench 达 67.5（Gemini-2.5 Pro 51.5）[10]；MindCube 专项模型达 90% [11]。但 Cambrian-S 作者承认「多加几个房间就失效」「仅扩大 token/上下文/模型规模不够」[10]，泛化与长时程一致性未解。正确表述是：**模型空间能力正在快速改善，但短期内仍需结构化中间层**。另一个常被引用的「CoT 有害」结论只对 2024 年模型零样本提示成立；2025–2026 原生思考模式普遍带来 5–7 分提升 [9][3]，有效的是「带显式空间结构的推理」而非纯语言链——这意味着中间层应输出模型能在其上推理的结构（网格/图/程序）。

**第二层：「只能用代码表达」——不成立，这是手段不是问题。**

所有主流 AI-3D 系统都走「LLM 生成脚本/命令 → 引擎执行」：blender-mcp 的 execute_blender_code、SceneCraft 生成 Blender Python、NVIDIA ChatUSD 生成 USD 脚本 [95][14]。Unity 官方文档称 `unity command/eval`（直接执行 C#）比 MCP「faster and use fewer tokens」[46]，社区实践者也证实让 AI 写 Editor script 建 prefab/scene 比直接写 .prefab/.unity 文件效果更好、token 少得多 [55]。代码是 LLM 最擅长的模态，而且即便做了中间层，最后一公里仍是代码。**P1 真正的问题在于喂给代码的空间表示**：

- 让通用 LLM 直接写数值坐标（LayoutGPT 范式）在 3D-FRONT 上出界率 GPT-3.5 版卧室 43.26%、客厅 73.58%；GPT-4 版 51.06%/64.15%（经专门训练的非 LLM 基线 ATISS 更差：49.88%/83.02%，说明出界是室内布局生成的普遍难题）[15]。LayoutVLM 复测 LayoutGPT 房内率仅 24.2% [17]。
- 换成关系约束 + 求解器后：Holodeck 消融 MRR 约束法 0.706 vs 绝对坐标 0.364 [12]；R3L（2026-05，GPT-5 + 可微约束）碰撞/越界 0.0/0.0，用户研究 Elo 1905 vs LayoutGPT 1511 [18]。Open-Universe 给出的机制解释是「度量坐标与绝大多数自然语言文本不匹配」[13]。
- 2026-05 的 3D Primitives/SpatialBabel 进一步显示：同一模型的物体检测 F1 跨六种场景代码语言（Three.js / Unity C# / Blender Python / Open3D / JSON / DSL）相差最高 5.7×；Claude Opus 4.7 最佳 Three.js .792、最差 DSL .615 [27]。**导出格式本身是影响 AI 读写效果的关键变量**。

**注意反例**：「拒绝直接输出坐标」是免训练提示路线的主流选择而非全部——LayoutGPT、DirectLayout（SFT+DPO 微调 Qwen2.5-32B，出界率压到 8.74%）[16]，以及经训练的 SceneScript/SpatialLM 都直接输出数值坐标 [19][20]。但这些都需要训练且限室内分布。

### 1.2 P2：用户脑中的场景与 AI 搭出的有出入，根因是自然语言无法充分描述三维

**判定：成立。** 这也是反方 A 明确承认「反驳不了」的一条。

**一手实测（引擎内）**：

- Classmethod（2026-03-08，Unity 6000.3.10f1 + 官方 com.unity.ai.assistant 2.0.0-pre.1 + Claude Opus 4.6 经 Claude Code）：在 TPS 关卡北端加房间，12 个物体全部生成，但「原有墙体堵在门口」「带天花板的房间内无任何灯光」「房间相对相邻墙体过大」、全部用 URP 默认 Lit 材质、Static Flags 全关；AI 只做了一次四视角外部截图、从未把相机移进室内；夜战任务中 AI 把自己的截图判为「almost complete darkness」而作者 Play 视角可正常操作 [53]。注意该测试走 Claude Code → Unity MCP 路径，早于 Open Beta，不涉及 Unity 自家 Agent 模式。
- Magnopus（2026-10-13，UE 5.8 官方 MCP + Copilot/Gemini CLI）：AI 能在精确坐标 spawn 静态网格和点光源，但「initially placed wall segments around a single center tile rather than along the room perimeter」、「Correct wall positions, wrong orientation. Corners not included」、「routinely placed chairs facing away from desks and clipped tables halfway into walls」；灯具因未命名无法区分吊灯/台灯。作者归因为模型「working off coordinate math」、缺乏空间直觉，并称「an experienced artist can often transform or duplicate objects in the editor faster than prompting an AI assistant」[65]。
- Puget Systems（2026-07-09，UE 5.8 + Claude Opus 4.8）：灰盒走廊 + 6 房间约 5 分钟搭出「大致符合」但作者未核验尺寸；每提示 5–15 分钟；小规模实验耗掉约 15% 周配额并在中午前耗尽会话额度 [67]。
- top3d（2026-06-24，UE 5.8 原生 MCP + VibeUE + Claude Code，作者有推广 Tripo 与付费课程的商业倾向）：「空间视觉是天花板——构图由你来定，搭建由它执行」，AI「不会复刻一张概念图」[68]。

**社区声音**：腾讯研究院胡璇（36氪，2026-04-16）访谈中 24 小时做出 3D 多人对战游戏的工程师认为最难的是「准确描述脑海中的画面」[105]；V2EX 用户「我让盾牌竖着放，修改了一遍又一遍，在地图里面还是横着摆放的」[106]；资深 TA 杨超wantnon（知乎，220 赞）：「图形上的瑕疵很难用语言描述，描述不准甚至还会误导」[107]；知乎 MrLiu 把「路线引导、难度曲线、空间压迫感」与「画面统一性、材质气质、色彩情绪」列为必须人类强把关的任务 [108]。日本工程师（note.com，2025-05，claude-3.7-sonnet）：「Scene 的编辑与细微调整最终手动更快」。

**理论支撑（为「人画、AI 读」分工背书）**：

- LLM 读结构化空间好、写差：ACL 2025 TSG-Bench 评测 11 个 LLM，「perform well on scene graph understanding, they struggle with scene graph generation」[26]；Text2Space（2026-04）提出 Read-Write Asymmetry [23]。
- 文本符号栅格比纯像素可靠得多：15×15 栅格渲成字符 vs 实心方块，Claude Opus 单元格准确率 90.6% vs 66.9%，ChatGPT 5.2 91.3% vs 65.9%（样本仅 15 张图，预印本）[24]；SpatialEval（NeurIPS 2024）GPT-4V Spatial-Grid 文本 0.923 vs 纯视觉 0.668，且「有足够文字线索时模型会少看图」[25]。
- SPACE 中同一任务由图像改为文本呈现，GPT-4o 平均从 40.1% 升至 65.2% [5]——精确文字已比图像更易被利用，但全局一致性仍有缺口 [9]。

**边界**：被引案例多为单次、单作者、早期版本的轶事，部分根因是工具链缺陷或 prompt 自身约束（例如 note.com 「红 Cube 不变红」实为 MCP 连接故障；zuqqhi2 的「全是基本几何体」是作者 prompt 的要求）。但三类环境独立复现同类错误足以说明「常见」，只是在统计意义上不能证明「普遍」。P2 的失效边界是：场景越依赖高度差、遮挡、视线、非标准朝向、越偏开放世界而非室内家具，文字与 2D 草图越失效。

### 1.3 P3：上色/配色——AI 不知道用户具体想要什么色彩、材质和风格

**判定：部分成立。**

**成立的部分（文字描述颜色/风格是实证瓶颈）**：

- GenColorBench（2025-10）评测 9 个 T2I 模型：命名色准确率 29.55%–49.85%；RGB/hex 数值色 9 个模型中 6 个低于 10%（高于 10% 的是 Sana 15.80%、OmniGen2 17.49%、BLIP3o 28.31%）[78]。扩散模型会把「jungle green」长出丛林、「Duke blue」写出 DUKE [81]。
- VLM 看图读色不可靠：ColorBench（NeurIPS 2025，32 个 VLM）最佳约 60%，颜色比例任务「only slightly better than random guessing」[80]。所以不能指望 AI 从参考图/截图里准确读出颜色，颜色要在中间层数值化。
- LLM「情绪词 → 颜色」最不可靠：GPT-4o 预测人类颜色-词联想在 Emotions 类表现最差 [83]。「暖色黄昏、低饱和、Ghibli 风」交给 LLM 自行翻译方差大。
- Scene Language（CVPR 2025 Highlight）的论证：外观身份「hard to describe but easy to recognize」，需用嵌入/参考图而非文字 [21]。

**已被解决的部分（作为沟通问题）**：

- LLM 对 hex 的理解相对可靠：ColorGPT（ICDAR 2025）色板补全 Hex 52.60% / RGB 42.86% / 纯色词 17.06%；整色板生成任务上最佳编码是「色词 + hex 混合」[79]。GPT-4 凭 hex 预测人类颜色联想 r≈.67 [83]。**结论：导出 hex 加语义词，而不是只给形容词。**
- 参考图槽已是产品标配：Unity Sprite Generator 六种参考算子 + Strength 滑块，Cubemap Generator 用 Image Reference 定「color palette, lighting tone」，Material Generator 文本 + Pattern Reference [45]；Meshy AI Texturing 接受参考图 + 预设风格 [90]；IP-Adapter（22M 参数）让参考图与 ControlNet 结构控制并用 [84]；StableGen 已用它为整个 Blender 场景投影贴图 [85]；R2C 插件把参考图直接转成 UE LUT [86]。
- 社区已把 art bible 编成 Agent 可读文件：art-bible skill 导出 palette.json（name/hex/rgb/role）、palette.css、style-anchor-prompt.md [87]。传统美术团队也靠「视觉工件 + 简短语义词汇」而非开放式文字：Beast Breaker 色彩脚本的「黄=安全、白=主角、品红=腐化」词表 [88]、Firewatch 以一张海报为唯一视觉基准 [89]。

**仍未解的部分**：

1. AI 默认不会主动匹配项目既有风格：Classmethod 新物体全用默认 Lit、夜景任务天空盒仍是白天 [53]；日本开发者（CoplayDev/unity-mcp）同样报告「マテリアルの不一致」频发。但这是「Agent 没查项目材质库」的问题，一条 skill 规则 + 项目材质清单作为上下文可绕开大半。
2. 风格化（非写实）材质生成是 AI 材质的公认弱项：「Stylized or hand-painted aesthetics are difficult to achieve — outputs lean toward photorealism」，AI 有时把光照烘进 albedo、metallic 值出错 [93]。
3. 多资产风格一致性没有可靠解法：Meshy/Tripo/Rodin/Hunyuan 公开 API 无跨资产风格锁定参数（Meshy art_style 已弃用）[90]；反例是 Sloyd API 支持 style ID 让一批生成共享风格 [92]、Hyper3D Enterprise 提供 custom LoRA [91]，但 20–50 件同关卡风格统一的独立案例未能核实。

**对中间层的含义**：P3 的中间层增量是「取色器 + 参考图槽 + 材质语义标注」绑定到具体体块并导出为 hex/色板/LUT；这个增量真实但不足以单独构成产品。2 与 3 是生成模型的美术能力问题，中间层解决不了。

### 1.4 P4：AI 只能用简单几何体堆叠

**判定：部分成立。** 要区分「不会搭」与「没有资产 / 不会用资产」。

**「不会搭」——不成立，灰盒是标准第一步而非能力上限**：

- Unity 官方把 Generators 产物定义为「Credible enough to validate a mechanic, but intended to be replaced before ship」，3D Object Generator 输出标准 prefab，「can be replaced with final art at any point… the prefab reference stays in place」[48]。「先占位、后替换」是官方认可的工作流。
- 研究界的「结构先行」系统（WorldGen、Marble Chisel）都把体块当中间表示：WorldGen 让 LLM 只输出 JSON 参数 → 程序化 blockout + navmesh → 深度条件扩散 → image-to-3D → AutoPartGen 拆解，「让图像生成器决定一个方块是树、石还是房子」[29]；3D Primitives 论文甚至把 primitive 代码定位为 VLM 的「空间语言」[27]。
- 可核实的社区教程与 MCP 自带 demo 确实停留在 primitive 级（「Create a red cube with physics at position 0, 5, 0」、「以半径 2 圆形排列创建 3 个立方体」）[52]，但这反映的是示例选择而非能力边界。

**「没有资产 / 不会用资产」——成立，且是真正的瓶颈**：

1. **资产通道存在但尺寸不可硬约束**：Meshy Resize API 只有 resize_height / resize_longest_side / auto_size 三个互斥参数，等比缩放到米制单一尺寸 [90]；Tripo auto_size 同样等比；Rodin bbox_condition 为 3 整数「比例」且官方 Gen-2.5 规范未列该参数；Hunyuan3D-Omni 开源模型接受 bbox 但编码为「长宽高比例 → 8 顶点」，无任何贴合度指标，3.3B 参数需 10 GB VRAM，社区报告约 10 分钟/件且无贴图、2026 年无维护活动 [40]。「把 2×3×4 m 的盒子换成木屋」必须靠「生成 → 读包围盒 → 等比缩放贴地 + 非等比微调（会拉伸贴图）或重生成」——blender-mcp 源码明示生成资产「arrives at arbitrary scale and facing」，缩放交给调用方 [95]。
2. **AI 不会主动用场景里已有的资产**：虚幻仙贝实测中 AI「未使用场景中的足球门模型」[69]；Epic 为此在 5.8 加入 Experimental 语义搜索插件与 SemanticSearchToolset [60]，但 Fab 无公开 API [59]，Unity Asset Store 亦无官方 API 声明。
3. **生成资产离 production-ready 有「persistent gap」**：需满足拓扑、UV、PBR、骨骼绑定等引擎级约束 [94]；top3d 实测首版贴图 UV 拉伸、大件超 2 万面导入限制、原生 UE MCP 只能导 FBX/OBJ [68]。
4. **PCG 搭不出来**：Puget 要求的「PCG 城市」看起来对但「nothing had actually been built using PCG」，是手摆静态网格，之后迭代数小时未收敛 [67]——而 Epic 5.8.x 注册表实际含 31 个 PCG 工具（create_graph / add_node / connect_node_pins 等）[62]，Epic 文档也承认「没有 skill 上下文时 LLM 会误用节点」[122]，所以瓶颈在模型对 PCG 的理解与工具启用，不在引擎缺接口。
5. **「体块 → 可编辑可玩的引擎关卡」未被任何产品闭合**：Marble 产出高斯泼溅 + 粗碰撞网格 + 整体重建网格（约 60 万三角面带贴图，最长 1 小时，有洞/浮面伪影），进 UE/Unity 依赖第三方 splat 插件、丢动态 GI [32]；WorldGen 不开放；HY-World 2.0 完整管线约 80B 参数 [43]。

**成本量级**：30 件资产云端生成约 $12–25、机器时间 1–1.5 小时串行可并行 [90][91]；对 MVP 可接受。真正的成本在人工尺寸校正与风格审核（无实测数据，属推论）。

## 2. 现有方案全景

### 2.1 六类路线

**A. 学术中间表示路线**：Holodeck（10 类关系约束 + DFS 求解）[12]、Open-Universe（嵌入 Python 的声明式 DSL + 梯度下降）[13]、SceneCraft（关系二分图 → Blender Python，去关系图后约束得分累积消融由 88.9 跌到 3.2）[14]、LayoutVLM（带 2 m 坐标网格与朝向箭头的标注图 + 数值初值 + 5 种约束 DSL + 可微优化，房内率 94.9%；消融显示三者任一缺失都明显掉分：去渲染图 PSA 58.8→48.2，去视觉标记 →43.0，去约束优化 IB 94.9→14.1）[17]、R3L [18]、SceneScript（make_wall/make_door/make_bbox，5 cm 量化）[19]、SpatialLM（Python dataclass 式 Wall/Door/Window/Bbox）[20]、Scene Language（程序 + 词语 + 嵌入）[21]。游戏关卡侧：MarioGPT 瓦片字符串、AIIDE 2024 综述指出 102 篇关卡生成论文多为 2D 且「3D 关卡远比 2D 复杂」[119]、数据库驱动的 3D 多层关卡框架 [124]。**解决了**：LLM 不直接吐坐标也能出物理合法布局。**没解决**：全部限室内家具/2D 瓦片，无户外地形、多层结构、可玩性约束；中间表示仍由 LLM 生成，没有承载用户脑中的具体长相。

**B. 引擎内置 AI**：Unity AI（2026-05-01 Open Beta，Ask/Plan/Agent、scene creator skill 可「丢一张图 → primitives/占位搭场景」、Generators 含「Scene layouts from image references」、官方 MCP server 现免费无并发限制）[44][45][123]；Unity CLI（`unity eval/command/mcp`，1.0.0-beta.13，Experimental）[46][47]；Unity 官方 Claude Code 插件（unity-agent-plugin + skills 34 个技能、无场景布局技能）[49][50]；UE 5.8 Unreal MCP（2026-06-17，Experimental，本地无鉴权、工具串行；Toolset Registry 约 52 toolset/824 工具，含 Actor/Scene/Primitive、Blueprint 图编辑、PCG 31 工具、语义搜索、带标注的 epic_capture_viewport）[59][60][62]；团结引擎 2.0 + Tuanjie AI（2026-07-28 发布会；「对 AI 更友好的新数据格式」只有一句定性描述，2.0 截至 2026-10-17 未上线；CEO 承认「把这盏灯变成绿色」这类增量修改仍常出错）[57][58][114]。**解决了**：Agent 可读写场景层级、Transform、组件、材质，可批处理，可截图。**没解决**：无布局精度文档、无「用户先画 3D 意图」的输入端、多步任务不可靠（soleron：「Mediocre planning capabilities… made up its own screen flow」，14 天后停用）[54]。

**C. MCP / Agent 工具（社区与商业）**：Unity 侧 CoplayDev/unity-mcp（15.1k star，v10.3.0，50 工具含 manage_probuilder/batch_execute/execute_code）[51]、IvanMurzak/Unity-MCP（4.5k star，四种截图，ProBuilder/Terrain 扩展）[52]；UE 侧 db-lyon/ue-mcp（2040+ 动作，可包装 Epic 824 官方工具）[62]、Ludus AI（有「自动放占位体 → 批准后替换最终网格」流程）[115]、MapForge（YAML/JSON 规格 → 确定性灰盒关卡）[102]、AgenticLink（BatchPopulateLevel 一次完成多物体生成/变换/父子）[103]；Blender 侧 blender-mcp（31.4k star，get_scene_info 每物体一行、look 多角度、generate_3d 接三家生成器）[95]、blender-orchestrator（真实尺寸库、ASCII 平面图、碰撞校验）[96]、Discussion #362 的 SKILL.md 自动检查穿模/悬空 [97]。**解决了**：接口全、批处理可用、Blender 侧已有空间校验层。**没解决**：全是「聊天 → 工具调用」范式，无 3D 意图输入；大场景全量 hierarchy 撑爆上下文（23 万实例 ISM 压死 ue-mcp 服务器、Unity 侧 38–42 分钟挂死事故）[63][51]；工具目录开销远大于物体操作（MifBridge 懒加载后每请求 134,569 → 3,900 token）[104]。

**D. 3D 资产生成**：Meshy 7.1（插件覆盖 Unity/Unreal/Blender、API/CLI/MCP）、Tripo、Hyper3D Rodin Gen-2.5（ControlNet 支持 bbox/体素/点云比例）、Hunyuan3D 2.x/Omni、Roblox Cube（scene layout generation 列为 upcoming）、Seed3D 2.0（部件分割、URDF 铰接、微调 LLM 做布局规划，面向具身智能，论文不提游戏引擎）[41]。**解决了**：单个物体长什么样。**没解决**：硬尺寸约束、跨资产风格锁定、场景级布局。

**E. 世界模型**：Marble/Chisel [30][31][32]、Meta WorldGen（不开放）[29]、HY-World 2.0（宣称可直接导入 Unity/UE，完整管线 80B 级）[43]、腾讯 WorldClaw（规划 Agent 把文本转为区域/地形/资产/材质/空间关系结构化规格，输出可编辑实例级资产，代码未放出）[42]；Genie 3 / Odyssey-3 / Runway GWM / HY-WorldPlay / 微软 Muse 全是实时视频型，无几何可导出。世界模型公司商业重心偏向机器人/仿真（World Labs 加入 AMD、NVIDIA 把 Marble 场景导入 Isaac Sim）。**解决了**：一句话/一组体块出整个风格统一的环境。**没解决**：逐物体可编辑、引擎原生渲染管线、精确结构保真（Chisel 无独立实测）。

**F. 场景级 / 草图输入 AI 工具**：Sketch2Scene（草图 → 2D 布局 → Unity/UE PCG，无引擎集成代码）[39]、Level Prototyper（单 HTML 灰盒工具，导出 JSON/GLB/OBJ/PNG + 三引擎包，$1 起）[100]、vibe-stack/three-maps（R3F blockout 编辑器，MIT，无 glTF 导出无 AI）[101]、wassermanproductions/blockout（影视 AI 预演：灰盒 → 参考视频/深度图/俯视 blocking 图/prompt.txt）[98]、updream 预演台（AI 视频「3D 白模作空间锚点」）[111]、VibeGame（声明式 XML parts）[99]。**解决了**：「人摆体块 → 导出 AI 可读包」在影视与 Web 游戏领域已被做出。**没解决**：核查范围内没有一个面向 UE/Unity + LLM 编码代理、带语义/参考/配色层的产品。

## 3. 「中间层」方案可行性评估

### 3.1 技术路线对比

| 路线 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| **独立 Web 工具**（R3F + drei + Zustand + GLTFExporter，起点 three-maps）[101] | 无需装引擎、10 分钟上手、跨引擎；一人 1–2 月可出极简 MVP（three-maps 单人约 5.5 月 166 commits 做出编辑器 + 平面图，Level Prototyper 单人出三引擎导出包）[100] | 重造阉割版编辑器；多一道导入导出（坐标系：glTF Y-up 右手米制、Unity Y-up 左手米制、UE Z-up 左手厘米）；与引擎内 blockout + MCP 读层级正面竞争；面对 Marble Chisel 心智占位 | 反方 B 认为四种形态里最差。**不建议作为首发形态** |
| **引擎内插件**（Unity 先行） | 用户已在引擎里摆体块，无转换；直接复用 ProBuilder/Modeling Mode；Unity 官方 Claude Code 插件 + skills 链路现成且无场景技能 [49][50]；Unity MCP/CLI 免费 [123] | 每个引擎一套；可能被官方吸收 | **推荐**。价值放在语义标注面板 + 预计算关系导出 + 校验器 |
| **Blender 插件** | blender-mcp 31.4k star 已打通 blockout/文本化场景/视觉自检/资产生成 [95]；blender-orchestrator 已有尺寸库与校验 [96] | 用户目标是 UE/Unity，Blender 多一跳；增量空间被社区项目挤占 | 次选；可借鉴其「每物体一行文本 + 多视角渲染」双通道设计 |
| **仅导出规范 + Agent Skill** | 零 UI 成本；以「规范被采纳」换用户 | schema 无护城河（SceneScript/Holodeck 词表/LayoutVLM DSL/glTF extras/UsdSemantics 均已标准化）[19][12][17][120][121]；社区已有 art-bible/level-design skill [87] | 应作为引擎插件的一部分开源，不单独成产品 |

### 3.2 导出格式建议

证据链：LayoutVLM 消融显示「数值位姿 + 关系约束 + 带网格标签的渲染图」三者缺一掉分 [17]；文本栅格比纯像素可靠 [24][25]；FloorplanQA 显示 LLM 读 JSON 布局时距离/可见性类可达 85–99%（合成厨房）但放置可行性、最大空箱、最短路径大幅下滑（HSSD 真实布局上即便距离/可见性也降到 57–69%）[22]——**所以关系要预先算好写明，不要让 AI 从原始几何推断**；SpatialBabel 显示输出语言影响高达 5.7× [27]——**格式本身需作为实验变量**。

推荐组合：

1. **几何**：glTF/GLB（节点层级 + TRS + 体块网格），UE 走 Interchange「Import Into Level」（目前仅 glTF/MaterialX 可直接生成关卡 Actor）[72]，Unity 走 glTFast 或 UnityGLTF。
2. **语义层**：**独立 sidecar JSON（必须）**，可选同时写入 node.extras。字段：id、name、category、role（door/cover/spawn/landmark）、location（m，右手 Y-up 并附引擎换算说明）、size、yaw、parent、facing_target、relations（against_wall / on_top_of / adjacent / faces / line_of_sight_to / occludes，借 Holodeck 10 类关系词表与 LayoutVLM 5 种约束 DSL）[12][17]、material_intent（hex + 语义词 + 参考图路径，借 art-bible palette.json 字段）[87]、acceptance（可玩验收条件，借 CSDN「六项」中的入口出口/主支路/高差/地标/障碍/验收）[110]。
3. **视觉参考**：带 1 m 坐标网格、北向箭头、物体标签与朝向箭头的俯视 PNG + 2–3 个标注透视截图（仿 LayoutVLM 与 Epic epic_capture_viewport 的标注方式）[17][62]；可选 ASCII 语义栅格 [23]。
4. **调色板**：palette.json（hex/rgb/role/semantic word），可导出 Lospec .hex/.gpl；整体色调可另导 LUT 供 UE Post Process [86]。

**为什么 sidecar 而不是只靠 extras**：UE Interchange 原生 glTF translator 不暴露 node.extras，Epic 员工 2025-07 表示「没有设计扩展既有 translator 的方式」，短期答案是复制整个 translator [73]；UE 唯一有官方文档保证元数据存活的开放格式通道是 USD（customData → UsdAssetUserData，Python 可读回）[74]，但 USD 在 Unity 侧仍是预发布包。Unity 侧 glTFast 6.x 默认 schema 无 extras（7.0.0-exp.1 已加 ExtrasContainer 但为实验版）[76]，UnityGLTF 2.20 的 OnAfterImportNode 可在编辑器路径读 extras [77]。稳妥做法：sidecar JSON + 50–200 行引擎脚本，UE 写 Actor.tags / 组件 AssetUserData（有文档的创建路径是 add_asset_user_data_of_class）[74][75]，Unity 写 tag / layer / SemanticTag MonoBehaviour；Agent 经 Epic 原生 epic_get_tags / epic_get_properties 或 CoplayDev find_gameobjects(by_tag/by_component) 读回 [62][51]。

### 3.3 与 UE / Unity 的对接路径与工程量

- **Unity（优先）**：ProBuilder/Modeling 摆体块 → 插件面板标注语义/参考/色板 → 导出包（GLB + JSON + PNG）→ Claude Code 经 Unity 官方插件/CLI 或 CoplayDev batch_execute 一次读入、替换资产、设材质、打光 → 插件校验器检查并回传 Agent。官方 MCP server 现免费 [123]。工程量：导出 + 校验器约数百行 C#，Skill 为 Markdown。
- **UE**：Modeling Mode 体块 → 同上 → Python Editor Script（Experimental，运行时阻塞 UI）或 Epic 5.8 MCP 的 execute_tool_script（5.8.3 失败不回滚）[63] → 校验。已知坑：World Partition 下 Actor 工具只见已加载 cell；set_properties 非原子；CaptureViewport 的「可选」参数实为必填 [63][64]。
- **批处理可把 12–15 物体压成一次调用**（AgenticLink BatchPopulateLevel 替代「15 to 30+ sequential tool calls」[103]、unity-mcp batch_execute、UE execute_tool_script），但没有任何来源给出批处理前后的实测 token 数。

### 3.4 AI 读结构化文本 vs 读截图

不是二选一，是互补；但在当前实现下结构化文本应为主：

- 支持结构化为主：LayoutVLM 去掉视觉图像后位置/旋转一致性几乎不变（Pos. 77.5→79.1、Rot. 73.1→74.0），图像主要改善碰撞 [17]；WorldAuditBench 6.6–42.3% vs 人 83.4% [28]；SpatialBabel 重建 F1 高达 .937 的模型关系问答仍只有 35.7–38.2% [27]；Classmethod 的 AI 自评与人眼相反 [53]；Epic CaptureViewport 单次 >1M token、1.5–2.6M 字符，有用户请求 bIncludeImage=false 只返回标签 [64]——**若 Epic 落地「标签-only」返回，引擎侧就自带了结构化场景导出**。
- 截图仍有价值：Puget 的 AI 在 PCG 流程中自己截图评估 [67]；top3d 称「带标注的截图是原生 MCP 的强项」[68]；blender-mcp 的 look 工具是「check its own work」的标配 [95]。

### 3.5 最大风险

1. **增量不存在**：引擎内灰盒 + MCP 读层级可能已经等价于中间层导出（反方 B 的 strong 论点①）。只有对照实验能回答。
2. **失败在「写」端而不是「读」端**：输入再精确，执行端用的仍是同一个 Agent + 同一套 MCP，墙绕中心、椅背对桌照旧发生（Magnopus、Classmethod 都是在有精确坐标的情况下出错）[65][53]。中间层要靠**校验器 + 复合放置工具**（Magnopus OKO 的 composite placement shortcuts + preflight validation 就是这个方向）而非更好的描述来缓解。
3. **被官方吸收**：Unity Generators「图 → 场景布局」、Epic 标注截图、团结 2.0 新数据格式、UE6 内建 LLM [45][62][58][70]。
4. **资产层无解**：硬尺寸、风格一致性、production-ready gap 不是中间层能解决的 [40][90][94]。
5. **执行成本**：每提示 5–15 分钟、吃配额；描述越完整工具调用越多 [67]。
6. **市场**：可触达用户 = 在 UE/Unity 里用编码 Agent 搭 3D 关卡的开发者 ∩ 愿付费者，交集极小；同类独立工具信号弱（three-maps 95 star、Level Prototyper 无评论、Promethean © 2024 疑停更）[101][100]；gamesbyai.win 583 款浏览器可玩 AI 游戏中 Unity 5 款、Unreal 0（但该目录只收浏览器作品，有选择偏差）[112]。

## 5. 建议

### 5.1 MVP 范围定义

**做什么（Unity 6 插件 + Claude Code Skill，限室内/模块化关卡）**：

1. **语义标注面板**：对用户已在 ProBuilder/Modeling 里摆好的体块，一键标注 category、role（door/window/cover/spawn/landmark/path）、facing_target、参考图路径、hex 色板与材质语义词、可玩验收条件。
2. **关系预计算器**：自动算出 against_wall、on_top_of、adjacent、faces、line_of_sight_to、occludes、reachable（简单 navmesh 或射线）并写入 JSON。
3. **导出包**：sidecar JSON + 带 1 m 网格/标签/朝向箭头的俯视 PNG + 2–3 张标注透视截图 + palette.json；可选 GLB 与 ASCII 栅格。
4. **校验器**：门洞被挡、AABB 重叠 >5 cm、悬空（底面距地 >5 cm）、越出房间壳、带天花板房间无光源、尺度相对阈值、未匹配 JSON 的多余/遗漏物体——以 Agent 可读的 JSON 报告输出，作为 Skill 的验收步骤。
5. **Skill**：教 Claude Code 读导出包、经 Unity CLI/MCP 批量替换资产（先占位后替换，prefab 引用不动）、设材质（优先项目材质库，其次 hex）、打光、跑校验器、按报告修正，上限 N 轮。
6. **开源**：JSON schema、Skill、校验器全部开源。

**明确不做**：独立 Web 编辑器；资产生成与贴图生成；地形、植被、PCG 图；UE 版本（第二阶段）；风格一致性判定；任何「替代手搭」的宣称。

### 5.2 2–4 周内可做的验证实验（可量化）

**场景**：单间 8 m × 6 m × 3 m：4 墙 + 地 + 顶、南墙偏西 1 门、北墙 2 窗、靠东墙居中 1 桌、4 椅两两对坐面向桌、顶中 1 吊灯、桌面东北角 1 台灯、西墙 1 书架背贴墙，共 14 物体。人先在 Unity 6 ProBuilder 搭出 Ground Truth，脚本导出 GT JSON（name/category/location/size/yaw/parent/facing_target/relations）。

**四组输入 × 3 次重复，每次全新空场景与新会话，同一模型（当前可用的 Claude Opus/Sonnet 5.x）、同一工具集（CoplayDev core + probuilder，或 Unity 官方 MCP/CLI）、禁止 AI 截图（E 组除外）、上限 10 轮**：

- A：纯文字 ≤200 词、不含坐标。
- B：文字 + 标注俯视图 PNG。
- C：GT JSON 子集（位置/尺寸/yaw + 预计算关系，不含资产路径）。
- D：人搭灰盒后空会话，让 Agent 经 MCP 一次读全层级，再要求「不改布局，替换真实资产 + 材质 + 灯光」。
- 可选 E：B 组 + 允许截图，单独记成本。

**度量**（结果 JSON 按 name/category 匹配）：位置 RMSE（按房间对角线归一）、尺寸相对 RMSE、yaw MAE、朝向正确率（椅面向桌、门窗在正确墙、灯在顶/桌上）、AABB 重叠 >5 cm 计数、越出房间壳计数、遗漏/多余物体数、对话轮数、总 token（Claude Code `/usage` 的 Session 块或 OpenTelemetry）[118]、MCP 调用数、墙钟时间、达到「可接受」所需手动编辑次数。

**成功标准**：C 组位置 RMSE 与朝向正确率显著优于 A（如 RMSE 减半、朝向正确率 +30 个百分点），且 C 不劣于 D。**判读规则**：若 C ≫ A/B 且 C ≈ D，则中间层价值只剩「不开引擎 + 预计算关系 + 语义/色彩标注」，应做插件而非独立工具；若 D ≫ C，放弃独立输入端，只做标注 + 校验插件；若 A ≈ C，重新审视 P2。

**预算与坑**：参照 Puget（4 项小实验耗 Pro Team 周配额约 15%）[67]，12–15 次完整运行可能达周配额 40–60%，预留数日或用 API 计费；用非 World Partition 场景；Unity 截图不含 UI；注意 LayoutVLM 的先验——图像主要改善碰撞而非位置/旋转 [17]，所以 B 与 C 必须分开测。

### 5.3 技术选型与起点开源项目

- **Unity 插件**：C# Editor 脚本 + ProBuilder API；导出用 UnityGLTF（extras 可读写）[77]；校验器用 Physics.OverlapBox / Bounds / 射线。
- **Skill**：仿 Unity-Technologies/skills 结构 [50] 与 art-bible skill 的 palette.json 字段 [87]；参考 mcp-for-blender Discussion #362 的几何 QA 清单 [97] 与 blender-orchestrator 的真实尺寸库 [96]。
- **Schema**：Holodeck 10 类关系词表 [12]、LayoutVLM 5 种约束 [17]、SceneScript 命令集 [19]、Tiled 对象层字段、glTF extras/KHR_xmp_json_ld [120]、UsdSemantics 标签 [121]——无需自创。
- **若日后做 Web 版**：fork vibe-stack/three-maps（MIT）[101]，补 GLTFExporter、语义层、俯视截图。
- **UE 第二阶段**：Python Editor Script + Interchange Import Into Level（glTF）+ sidecar JSON 写 Actor.tags/AssetUserData [72][74]；或注册为 5.8 自定义 toolset。

### 5.4 差异化定位

一句话：**不是「让 AI 摆方块的工具」，而是「把人已经决定的空间意图无损传给 AI、并替 AI 做验收的插件」**。差异点在校验层与意图层——这恰是 Magnopus/OKO、blender-orchestrator、Discussion #362 社区在自发补、而官方工具清单里最缺的东西 [65][96][97]。与 Marble Chisel 互补（它做风格化环境，你做可编辑关卡）；与引擎官方 Agent 互补（它们是执行端，你是输入端 + 验收端）。接受这更像「能被 Unity/Epic 吸收或变成社区标准的工具」，而非独立长成公司的产品。

## 6. 未解问题与下一步调研

1. **核心对照数据缺失**：没有任何「纯文字 vs 结构化 vs 图像 vs 引擎内灰盒」在 UE/Unity 内的还原度实验（CraftBench-UE、LatticeWorld、AutoUE、Zero-shot 3D Map 均无此消融）[38][36][35]——这是你自己要做的第一个数据点。
2. **UE Interchange glTF 导入是否保留 node.extras**：仅有 2023/2025 论坛口径，5.8 源码未核；需用带 extras 的 glTF 实测 [73]。
3. **Epic 是否会为 CaptureViewport 增加 bIncludeImage=false**：若落地，引擎侧自带结构化导出，直接影响中间层必要性 [64]。
4. **团结引擎 2.0「AI 友好新数据格式」的实际形态**（JSON/DSL？是否对外部 Agent 开放？）：零细节，2.0 未上线 [57][58]。
5. **Marble Chisel 结构保真度**无独立实测；World Labs 入 AMD 后 Marble/World API 去向未公布 [33]。
6. **Unity Generators「Scene layouts from image references」**是否直接落地到场景、精度如何：官方无文档 [45]。
7. **大场景规模上限**：Epic 原生 find_actors 在 500/2,000/10,000 Actor 的表现无公开报告；Unity 侧只有 13.3k token 单响应与 38–42 分钟挂死两个事故点 [63][51]。
8. **中文一线来源**：知乎（403）、部分 CSDN（521）、Reddit 未覆盖；两篇关键 CSDN 实测文（陶嘉恒、SainAI_）疑为 AI 辅助/内容农场文 [109]；「网易伏羲简笔画地形」与「混元 3D 3.0 落地 15+ 场景」均**未核实**。
9. **输出语言差异**：同一 JSON 让 AI 生成 Unity C# / UE Python / 直接 MCP 调用三种落地路径的差异未测（SpatialBabel 显示 Unity C# 对部分模型最差）[27]。
10. **2026-10-12 之后的 Epic 动态**（AI-first 转向 [71]）与 Unity 2.x 系列文档变化需持续跟踪。
